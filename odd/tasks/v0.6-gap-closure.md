# v0.6 gap closure

Objetivo: cerrar los gaps de API/diseño reportados por tlacuache_app tras migrar a v0.5.0, más otros encontrados por análisis propio del código. Branch: `feature/v0.6-gap-closure` (crear desde `main`). Delivery: work-unit commits por tarea, PR al cierre. Test runner: `npm test` (Jest + ts-jest), `npm run verify:dist` antes de cualquier release.

## Specs

- S1 (tlacuache_app, gap 1): "`applyReplaceShadow` no está exportado públicamente. [...] Pedimos: (a) exportarla oficialmente desde el entrypoint público, y (b) idealmente que el shadow-swap recree también índices y triggers secundarios leídos de `sqlite_master`, para poder usarla en los 8 catálogos sin el patrón manual que mantenemos aparte."
- S2 (tlacuache_app, gap 2): "No hay API pública para resetear mutaciones `in_flight` atascadas ni para re-encolar `failed` en el outbox de `createPushEngine`. [...] Pedimos algo como `resetStuckInFlight()` y `requeueFailed()` expuestos por `createPushEngine`."
- S3 (contexto tlacuache_app, no es pedido de cambio): "`enqueue()` solo acepta un `Adapter`, no puede unirse a la misma transacción que el write de la entidad [...] mantuvimos `pending_mutations` como fuente de verdad del lado de escritura y solo usamos el kit para drenar la cola." — registrado como limitación conocida y fuera de alcance de este documento; no genera tarea.
- S4 (análisis propio, alto impacto): el cursor de paginación para tablas `upsert` solo se persiste al final de todas las páginas de un `fetch` async-iterable (`engine.ts`), no por página, pese a que cada página ya se commitea de forma independiente. Si el iterable lanza a media página, las páginas ya aplicadas no se reflejan en el cursor y el siguiente sync las re-descarga y re-aplica (sin pérdida de datos por ser `upsert` idempotente, pero con trabajo repetido potencialmente grande).
- S5 (análisis propio, alto/medio impacto): `createPushEngine` no ofrece ninguna señal para una mutación con `dependsOn` huérfano (id que nunca existió) — queda `pending` para siempre sin error visible ni forma de distinguirla de una dependencia legítima aún no resuelta.
- S6 (análisis propio, medio impacto): no existe API pública para cancelar/descartar una mutación `pending` que el consumidor decidió abandonar (p. ej. la entidad local fue borrada antes de enviarla); hoy queda huérfana para siempre.
- S7 (análisis propio, medio impacto): `ApplyResult` (tipo de retorno de `applyReplace`/`applyReplaceShadow`/`applyUpsert`) no se exporta desde `src/sync/index.ts`, mismo patrón de gap que S1 para quien llame estas funciones directamente.
- S8 (análisis propio, medio impacto, escalabilidad): `_nuup_push_outbox` no tiene índice sobre `status`/`next_attempt_at`; `processQueue()` hace table scan en cada ciclo sobre una cola grande.
- S9 (análisis propio, bajo impacto, backlog — no genera tarea en esta ronda): `assertIdentifier` acepta nombres de tabla/columna que son palabras reservadas SQL sin comillas, pero el SQL generado no las escapa, así que fallan en runtime con un error SQLite confuso en vez de un error de validación claro.
- S10 (análisis propio, bajo impacto, backlog — no genera tarea en esta ronda): `sync()` no ofrece reintento selectivo de solo las tablas que fallaron sin volver a correr `sync()` completo.

**T1** — Exportar `applyReplaceShadow` y `ApplyResult` desde el entrypoint público (`src/sync/index.ts`); recrear índices y triggers secundarios (leídos de `sqlite_master`, `type IN ('index','trigger')`, excluyendo índices autogenerados `sqlite_autoindex_*`) tras el shadow-swap. Risk: item 3 (contrato público, aditivo) + item 1 (cambia comportamiento de datos persistidos en el swap) → verificación independiente.

**T2** — `createPushEngine` gana `resetStuckInFlight()` (vuelve `in_flight` a `pending`, para recuperar de crash a medio push) y `requeueFailed(id?)` (reencola una o todas las mutaciones `failed`, reseteando `attempts`). Añadir `cancel(id)` para descartar una mutación `pending`/`failed` (S6). Risk: item 3 (API pública nueva, aditiva, baja complejidad) → sin verificador independiente salvo que la implementación toque concurrencia (ver T3).

**T3** — Detección de `dependsOn` huérfano: validar en `enqueue` opcionalmente, o exponer el estado en `listByStatus`/`getQueueState` (p. ej. marcar mutaciones cuyo `dependsOn` no corresponde a ningún id conocido). Decisión de diseño pendiente (ver pregunta abajo). Risk: item 6 potencial si cambia silenciosamente comportamiento existente — a evaluar.

**T4** — Persistir el cursor de paginación por página (no solo al final) para tablas `upsert` con `fetch` async-iterable, para que un fallo a media página no pierda el progreso de cursor ya commiteado. Risk: item 1 (formato/semántica de dato persistido, cursor) → verificación independiente obligatoria.

**T5** — Añadir índice compuesto `(status, next_attempt_at)` sobre `_nuup_push_outbox` en `ensurePushOutboxTable`. Risk: item 1 (migración de tabla existente, aunque aditiva) → verificación ligera (comprobar que la migración es idempotente y no rompe datos existentes).
